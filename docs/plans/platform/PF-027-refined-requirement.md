# PF-027 — Refined requirements

> Living document. The backlog entry or the user's description was the starting point; this is the complete, current requirement as clarified in conversation, and it wins over the original wording. It says **what** to build; the plan says **how**. Sole author: the background refinement agent.

**Ticket**: PF-027 — One CI/CD pipeline with a staging environment and production releases from tags · **Plan**: [PF-027-staging-pipeline.md](PF-027-staging-pipeline.md) · **Master plan section**: `../portfolio-implementation-plan.md` §2 (CI/CD row) and §8 · **Status**: **Confirmed** · **Last updated**: 2026-11-25

## 1. Problem and goal

Since PF-013 three workflows (`backend.yml`, `frontend.yml`, `e2e.yml`) filter by path, and a push to `main` deploys each app straight to production after its own checks. There is no staging environment, the backend deploy job ends when Render accepts the hook so a green run does not mean the new version is live, there are no GitHub environments, the `main` ruleset does not require a pull request or checks, actions are pinned to tags rather than commit SHAs, and secret scanning, push protection, and Dependabot alerts are off. The owner wants one GitLab-like pipeline per commit that follows industry practice, and a staging environment that exists before he links the portfolio from his CV publicly. A push to `main` deploys to staging; production deploys only when the owner pushes a release tag. The audience is the owner, who verifies changes on staging before releasing them, and indirectly recruiters and hiring managers, who must only ever land on the verified production site. No production visitor-facing behavior changes.

## 2. Scope

**In scope**

- One workflow that runs changes detection, the checks, a single `ci-ok` gate job, the staging deploy, and a live smoke test for every pull request and `main` push, and a release gate, production deploy, smoke test, and GitHub Release for a release tag (D1, D2).
- A staging stack on free tiers, isolated from production data: a Vercel preview deployment at a stable address, a second Render Free service, and a separate Neon project; staging reuses production's Resend key (D9, D10, D20).
- Deploy verification: a public `GET /actuator/info` that reports the deployed commit and the environment name, and a live browser smoke test after every deploy (D12, D20).
- One backend environment name (`APP_ENVIRONMENT`) that marks contact emails sent outside production with a subject prefix and a Resend tag (D20).
- A "Staging" badge in staging builds only (D11), and the deployed version in the footer (D21).
- GitHub environments `staging` and `production`, a stronger `main` ruleset, a tag ruleset, SHA-pinned actions, and the free GitHub security features (D8, D13).
- Docs updates.

**Out of scope (deferred)**

- Pull-request preview deployments: Dependabot pull requests cannot read repository secrets, and staging covers the need (PF-013 D6 still applies).
- Automatic rollback on a failed production smoke test: a manual run from the previous tag is enough for a solo project.
- Promoting one built artifact, such as a container image in GHCR deployed to an image-backed Render service: it would need the production Render service recreated, so per-environment builds from the same commit are accepted.
- A manual approval button for production: the release tag is the owner's approval.
- Any keep-alive pinger, a custom domain, and a merge queue: the pool of Render hours rules out a pinger (D5), a custom domain is not needed, and a merge queue is not available for personal-account repositories and not needed solo.
- Creating the Vercel, Render, Neon, and Resend resources and the GitHub settings: these are owner steps listed in the plan.

## 3. Functional requirements

- **FR-1**: A single workflow runs for every pull request and every push to `main`: changes detection, then the backend, frontend, and end-to-end checks, then one job named `ci-ok`. On a pull request only the checks for areas with changed files run; on a push to `main` (and a manual run on `main`) every check always runs. Source: default 2026-11-25, D1, D15
- **FR-2**: `ci-ok` is reported on every pull request and every `main` push, including docs-only changes. It is green when every check passed or, on a pull request, was skipped because its area is unchanged, and red when any check failed or was cancelled. Source: default 2026-11-25, D1
- **FR-3**: After `ci-ok` is green, every push to `main` and every manual run on `main` deploys both apps to staging automatically, whatever files changed. Source: clarified 2026-11-25, D3, D6, D15
- **FR-4**: After each staging deploy, a smoke test opens the staging site with `?notrack=1` and checks that the content renders, a deep link to a project page renders, and the API status reaches online, plus the per-environment checks in FR-22. A failed smoke test fails the run. Source: default 2026-11-25, D12, D19
- **FR-5**: Pushing a release tag `vMAJOR.MINOR.PATCH` (for example `v1.0.0`) starts a release run that deploys production automatically once the gate in FR-6 passes. A tag can be created with `git tag` and `git push`, or by creating a GitHub Release on `main` in the UI or with `gh release create`. Source: default 2026-11-25, D4
- **FR-6**: A release run deploys to production only if the tag's commit is on `main` and either the `main` pipeline run for that exact commit succeeded (checks, staging deploy, staging smoke test) or that commit was already deployed to the `production` environment successfully before (a redeploy or rollback, checked against GitHub's deployment records). The existence of a GitHub Release is not the test, because the owner may create a Release in the UI to push a brand-new tag. Otherwise the run fails before touching production and its log says why. Source: clarified 2026-11-25, D3, D4, D16
- **FR-7**: A release deploys both apps, the whole state at that commit, in the order of FR-21, then runs the smoke test against the production site with `?notrack=1`. Source: default 2026-11-25, D6, D17
- **FR-8**: After a successful production deploy and smoke test, the pipeline creates a GitHub Release for the tag with generated notes if none exists yet, and leaves a Release the owner created as it is. Source: default 2026-11-25, D7, D16
- **FR-9**: A manual run from an older release tag redeploys that version to production through the same gate and smoke test (redeploy or rollback). Source: default 2026-11-25, D3
- **FR-10**: Each backend deploy waits until `GET /actuator/info` on the target API reports both the expected commit and the expected environment name, for a bounded time (about 15 minutes), then fails. The deploy is not green merely because Render accepted the hook, and a service started without the right `APP_ENVIRONMENT` fails here, before the frontend is deployed. Source: default 2026-11-25, D12, D20
- **FR-11**: `GET /actuator/info` (and HEAD) is public and read-only, returns 200 JSON with only the deployed commit and the environment name (for example `{"app":{"commit":"<sha>","environment":"staging"}}`, commit `local` when not on Render), and is not part of the OpenAPI snapshot. Source: default 2026-11-25, D12, D20
- **FR-12**: The staging build shows a small fixed badge labelled "Staging" with a link "Go to the live site"; the production build never shows it. Source: default 2026-11-25, D11, D18
- **FR-13**: Staging is isolated from production: its own Render service from the same Dockerfile, its own Neon project, and its own visitor-hash secret. It reuses production's `RESEND_API_KEY`, `CONTACT_TO_EMAIL`, and sender; there is no separate staging key. No production data is ever copied to it. Source: default 2026-11-25, D9, D10, D20
- **FR-14**: Staging is public ("anyone with the link"), not behind Vercel Authentication, and its responses carry `X-Robots-Tag: noindex`. Source: clarified 2026-11-25, D11
- **FR-15**: GitHub environments `staging` and `production` exist, each with its URL, its own Render deploy hook secret, and its site and API URLs. `staging` is deployable from `main` only; `production` only from tags matching `v*`. Source: default 2026-11-25, D8
- **FR-16**: The `main` ruleset requires a pull request (0 approvals) and the `ci-ok` status check (not strict about being up to date), and still blocks deletion and force-push. A tag ruleset protects `v*` tags from being moved or deleted. Source: default 2026-11-25, D13
- **FR-17**: Every third-party action is pinned to a full 40-character commit SHA with a version comment, and Dependabot keeps the pins updated. Source: default 2026-11-25, D13
- **FR-18**: Secret scanning with push protection, Dependabot alerts, Dependabot security updates, and CodeQL default setup (Java/Kotlin, JavaScript/TypeScript, GitHub Actions) are enabled. Source: default 2026-11-25, D13
- **FR-19**: Dependency review on pull requests fails on a new dependency with a high or critical vulnerability. Source: default 2026-11-25, D13
- **FR-20**: No keep-alive pinger runs against production or staging. Source: clarified 2026-11-25, D5
- **FR-21**: Within one environment the deploy order is backend first, then frontend: the backend deploy is started and the pipeline waits until `GET /actuator/info` reports the expected commit (FR-10); only then is the frontend deployed, and then the live smoke test runs. Source: clarified 2026-11-25, D17
- **FR-22**: The live smoke test also checks the badge and indexing per environment: on staging the badge is visible and the response carries `X-Robots-Tag: noindex`; on production the badge is absent. Source: clarified 2026-11-25, D19
- **FR-23**: The backend has one environment name, set by `APP_ENVIRONMENT`: `production` by default (production sets nothing new), `staging` on the staging service, `local` in the local profile. The value is lowercase letters only, and an invalid value stops startup. Source: clarified 2026-11-25, D20
- **FR-24**: Every contact email carries a Resend tag `environment=<name>`. Outside production the subject is prefixed with `[<name>] `, for example `[staging] New portfolio contact message (#12)`; production subjects are unchanged. Neither the tag nor the prefix carries personal data. Source: clarified 2026-11-25, D20
- **FR-25**: The site shows the deployed version in the footer. On production it is the release tag (for example `v1.0.0`). On staging it is the `git describe` value (for example `v1.0.0-3-gabc1234`, meaning three commits after `v1.0.0`), or the short commit SHA before any release tag exists. The version links to what changed: a release tag links to its GitHub Release notes, a describe value links to the GitHub compare view from that tag to the commit, and a bare SHA links to the commit. Nothing is shown in local development or tests, where no version is set. Source: clarified 2026-11-25, D21

## 4. Product rules and edge cases

- **API down or asleep:** staging behaves like production: the PF-023 waking state shows while the API wakes, and static content always renders (Non-Negotiable 1). The smoke test allows for the ~80 s wake-up.
- **Privacy:** staging stores visits under the same rules as production, with its own visitor-hash secret; no production data is copied; smoke tests use `?notrack=1` so no visit is counted; `/actuator/info` exposes the commit SHA and the environment name only, and no personal data (Non-Negotiables 3 and 9).
- **Abuse:** staging has the same rate limits and honeypot as production. Staging contact messages use production's Resend key, recipient, and sender, arrive with the subject prefix `[staging] ` and the Resend tag `environment=staging`, and share the Resend account's daily quota (100 per day) with production; this is an accepted risk (Non-Negotiable 4).
- **Shared Resend key:** revoking or rotating the key affects both environments until it is updated on both Render services; failed messages are resent later by the existing retry job. A staging service started without `APP_ENVIRONMENT=staging` would send unmarked mail, so the deploy check (FR-10) fails it before the frontend is deployed.
- A tag on a commit that is not on `main` is refused before any deploy.
- A tag on a commit whose `main` run failed or was skipped is refused, unless that commit was already deployed to production successfully before. A GitHub Release existing for the tag does not make it pass.
- When several commits land on `main` quickly, GitHub keeps only the newest waiting run, so some intermediate commits never reach staging and cannot be released; tag the newer commit instead. Because every `main` run deploys both apps, a successful run means that exact commit, both apps, passed every check and the staging smoke test.
- Every merge to `main` rebuilds the staging backend on Render (a few build minutes); this is accepted.
- The new frontend never talks to an older backend: the backend deploys first, so API changes must be expand-then-contract.
- Deleting or moving a release tag is blocked by the tag ruleset.
- Render's free build minutes and its 750 instance hours per month are one pool shared by staging and production; when the pool runs out every free service is suspended until next month, including production. This is why no 24/7 keep-alive runs (D5): production sleeps after 15 idle minutes and wakes in about 80 s, which PF-023 already handles in the UI.
- A failed staging deploy never touches production. A failed deploy or smoke test leaves the previous version live and is visible in the Actions tab; there is no automatic rollback.
- The badge copy and the endpoint hold no CV claim (Tier A).

## 5. Interface decisions

**API**: `GET /actuator/info` (and HEAD) is public and returns 200 JSON with the deployed commit and the environment name, for example `{"app":{"commit":"<sha>","environment":"staging"}}`, and commit `local` when not on Render. It exposes nothing else and is not part of the OpenAPI snapshot.

**Configuration and email**: `APP_ENVIRONMENT` (`production` default, `staging`, `local`; lowercase letters only, invalid value stops startup) is the single environment setting. Contact emails carry the Resend tag `environment=<name>`, and outside production the subject starts with `[<name>] `. No new setting on production.

**UI**: the staging badge is fixed, small, does not shift the layout, and has a keyboard-reachable link to the live site. It renders only in a build where `VITE_LIVE_SITE_URL` is set (set only in Vercel's Preview environment, which is staging) and its link points to that URL; production never sets it, so it never shows the badge, and no production URL is hard-coded in the frontend. The footer shows the deployed version (FR-25) as a link to the Release, the compare view, or the commit, and only in a build where the version is set. There is no other visitor-facing change.

**Content**: the badge copy, Tier A (no CV claim): label "Staging", link text "Go to the live site". The exact wording can be adjusted at approval.

## 8. Acceptance criteria (refined)

- **AC-1**: A docs-only pull request shows a green `ci-ok`, with the app checks skipped.
- **AC-2**: A pull request with a failing backend test shows a red `ci-ok` and cannot be merged.
- **AC-3**: Merging any change to `main`, even docs-only, runs every check and deploys both apps to staging, backend first and then frontend; the run shows the staging environment URL and a passing smoke test, and production is unchanged.
- **AC-4**: Pushing `v1.0.0` on that commit deploys both apps to production, the smoke test passes, and a GitHub Release `v1.0.0` exists.
- **AC-5**: A tag on a commit that is not on `main`, or whose `main` run failed or was skipped and which was never deployed to production before, fails before deploying and says why. A tag on an unverified commit still fails when the owner created a GitHub Release for it in the UI.
- **AC-6**: A manual run from an older release tag redeploys that version to production after passing the gate (commit already deployed to production successfully) and the smoke test.
- **AC-7**: `GET /actuator/info` on staging returns the deployed commit and `"environment":"staging"`, and the backend deploy step fails if the expected commit and environment do not appear within the bounded wait.
- **AC-8**: `GET /actuator/info` returns only the commit and the environment name, accepts GET and HEAD only, and is absent from the OpenAPI snapshot.
- **AC-9**: The staging build, where `VITE_LIVE_SITE_URL` is set, shows the "Staging" badge with a working link to that URL, and the production build, where it is unset, does not.
- **AC-10**: Staging responses carry `X-Robots-Tag: noindex`.
- **AC-11**: Staging's database contains none of production's rows, and its visitor-hash secret and database credentials differ from production's (it deliberately shares production's Resend key, D20).
- **AC-12**: The `staging` and `production` environments exist with their URLs and deployment policies, and a `staging` deploy from a tag or a `production` deploy from a branch is refused.
- **AC-13**: Pushing directly to `main` is refused, and moving or deleting a `v*` tag is refused.
- **AC-14**: Every third-party `uses:` in the workflows is a 40-character commit SHA.
- **AC-15**: Secret scanning, push protection, Dependabot alerts, Dependabot security updates, and CodeQL report enabled, and dependency review fails a pull request that adds a high-severity vulnerable dependency.
- **AC-16**: No keep-alive pinger targets production or staging.
- **AC-17**: The staging smoke test checks that the badge is visible and the response carries `X-Robots-Tag: noindex`, and the production smoke test checks that the badge is absent; a failing check fails the run.
- **AC-18**: In each environment the frontend deploy starts only after `GET /actuator/info` reports the expected commit.
- **AC-19**: A contact message sent on staging arrives with a `[staging]` subject prefix and Resend shows the tag `environment=staging`; a production message has no prefix and the tag `environment=production`; `/actuator/info` on staging shows `"environment":"staging"`.
- **AC-20**: A staging backend started without `APP_ENVIRONMENT=staging` fails the deploy check before the frontend is deployed, and an invalid `APP_ENVIRONMENT` value stops startup.
- **AC-21**: After a deploy, the footer version on the live site equals the version the deploy job computed (the release tag on production, the `git describe` value on staging), and the live smoke test fails when it does not. The version link points to the Release, the compare view, or the commit as described in FR-25.
