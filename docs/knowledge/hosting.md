# Hosting

Facts about Vercel, Render, and Neon observed on this site's own projects. Versions and defaults are as of the date in each entry.

## Vercel

### Vercel ignored `packageManager` and picked its own pnpm
- **Rule / Behavior**: For the project with Root Directory `frontend` and `ENABLE_EXPERIMENTAL_COREPACK=1`, Vercel's build warned "Could not enable corepack because package.json is missing "packageManager" property" although `frontend/package.json` declares `pnpm@11.0.9`, then installed with a pnpm that ignored the lockfile ("Ignoring not compatible lockfile") and failed with `ERR_PNPM_META_FETCH_FAIL … Value of "this" must be of type URLSearchParams`. With a version 9 lockfile, `vercel build` logs that the lockfile "may be generated by pnpm@9.x, pnpm@10.x, pnpm@11.x, or pnpm@12.x" and chooses "pnpm@10.x based on project creation date". Pinning pnpm in the commands themselves (`npx --yes pnpm@11.0.9 install --frozen-lockfile`, `npx --yes pnpm@11.0.9 run build`) installs with pnpm 11.0.9 whatever Vercel detects.
- **Source**: the first production build's log on Vercel; `frontend/vercel.json`
- **Verified**: the first deployment failed and the next one, with the pinned commands, succeeded; a local `vercel build --prod` with Vercel CLI 66.2.0 logged the detection lines and "Done in 1.6s using pnpm v11.0.9"; 2026-11-23
- **Discovered in**: PF-013

### `engines.node` overrides the project's Node.js Version setting
- **Rule / Behavior**: When `package.json` has `engines.node` (`^24.22.0`), Vercel ignores the Node.js Version in the Project Settings (26.x) and uses the matching major version (24.x), with a warning that names both.
- **Source**: `frontend/package.json`; `vercel build --prod` output
- **Verified**: local `vercel build --prod` with Vercel CLI 66.2.0; 2026-11-23
- **Discovered in**: PF-013

### The Vercel CLI runs from the repository root for a project with a Root Directory
- **Rule / Behavior**: With `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID` set, `vercel pull --yes --environment=production` run from the repository root writes `.vercel/project.json` (with `rootDirectory: frontend` and the dashboard build settings) and `.vercel/.env.production.local`. `vercel build --prod` from the root then builds `frontend/` with the `installCommand` and `buildCommand` from `frontend/vercel.json` when the dashboard commands are blank, writes `.vercel/output` (static files plus the SPA rewrite route) at the root, and also leaves files under `frontend/.vercel/static-build/`, which Prettier would check unless ignored.
- **Source**: the `deploy` job in `.github/workflows/frontend.yml`; `frontend/.prettierignore`
- **Verified**: local `vercel pull` and `vercel build --prod` with Vercel CLI 66.2.0, the dashboard commands blanked in the local `.vercel/project.json`; 2026-11-23
- **Discovered in**: PF-013

### A `VITE_` variable is a Config variable, not a Secret
- **Rule / Behavior**: Vercel's Add Environment Variable form defaults to the Secret type, which can never be revealed after saving. For a key with the `VITE_` prefix it warns that the prefix exposes the value to the browser and offers "Change to Config". `VITE_API_URL` is the backend's public address and ends up in the browser bundle by design, so it is stored as Config (readable later), and the prefix stays because Vite only bundles `VITE_` variables.
- **Source**: Vercel Project Settings → Environment Variables; `frontend/src/api/client.ts`
- **Verified**: adding `VITE_API_URL` for Production; 2026-11-24
- **Discovered in**: PF-013

## Render

### Root Directory `backend` builds the Dockerfile there and ignores other changes
- **Rule / Behavior**: A web service with Language Docker and Root Directory `backend` builds `backend/Dockerfile` with `backend/` as the build context, and Render ignores commits that change nothing under `backend/` for its own auto-deploys. The first deploy of `will-ly-portfolio-api` (Free, Singapore) took 3 min 16 s from start to live, including the Gradle build in Docker.
- **Source**: Render docs, Monorepo Support; the first deploy's Events and Logs pages
- **Verified**: first deploy, then `GET /actuator/health` answered 200 with `db` UP; 2026-11-24
- **Discovered in**: PF-013

### A deploy hook with `ref` deploys one exact commit and turns auto-deploy off
- **Rule / Behavior**: A `POST` (or `GET`) to the service's deploy hook URL starts a deploy. Appending `&ref=<commit SHA>` (full or short) deploys exactly that commit, answering 200 when the deploy starts and 404 when the SHA is not in the linked repository. Using `ref` turns the service's automatic deploys off, so the caller becomes the only path to production. The hook URL carries a key, so it is a secret.
- **Source**: Render docs, Deploy Hooks and Deploying a Specific Commit; the `deploy` job in `.github/workflows/backend.yml`
- **Verified**: Render docs read on 2026-11-24; the first run after the PF-013 merge exercises it
- **Discovered in**: PF-013

### A sleeping Free web service took 78.8 s to answer
- **Rule / Behavior**: After 15 minutes without requests, `will-ly-portfolio-api` (Free, Singapore, Spring Boot in Docker) slept. The next `GET /actuator/health` connected in 0.18 s, but Render held it until the service had started and answered after 78.8 s with 200; the next request took 0.31 s. The request is held, not refused, so a client timeout must be longer than the cold start: the site's 75 s timeout failed every first request after a sleep, and PF-023 raised it to 100 s.
- **Source**: `curl -w` timing of the health endpoint; `frontend/src/api/client.ts` (`COLD_START_TIMEOUT_MS`)
- **Verified**: one cold and one warm request at 08:02 UTC, 17 minutes after the previous request; 2026-11-24
- **Discovered in**: PF-023

### Maven Central rate-limits Render's shared build machines
- **Rule / Behavior**: Render builds Docker images on shared machines, and Maven Central answered their jar downloads with `Received status code 429 from server: Too Many Requests` (`repo.maven.apache.org`), failing `./gradlew bootJar` in the image build. The first deploy of the day passed and the next two failed, so it depends on other traffic from the same addresses. Resolving from Google's mirror of Maven Central (`https://maven-central.storage-download.googleapis.com/maven2/`) first, and caching the jars in the image's dependency layer, avoids it.
- **Source**: the Render build log of deploy `dep-dc2lm6brjlhs73d3tjo0`; `backend/settings.gradle.kts`, `backend/build.gradle.kts`, `backend/Dockerfile`
- **Verified**: two failed deploys at 09:39 and 10:30 UTC; a cache-free local build then downloaded all 566 files from the mirror; 2026-11-24
- **Discovered in**: PF-024

## Neon

### The JDBC URL comes from the direct connection string
- **Rule / Behavior**: Neon's Connect dialog shows a `postgresql://user:password@host/db?sslmode=require&channel_binding=require` string, with Connection pooling on by default (host ending in `-pooler`). With pooling off, the host loses `-pooler`; the backend then takes `DB_URL=jdbc:postgresql://<host>/<db>?sslmode=require`, with the user and password in `DB_USERNAME` and `DB_PASSWORD`.
- **Source**: Neon Console → Connect; `backend/src/main/resources/application.yml`
- **Verified**: the first Render deploy connected over the direct host and Flyway created `page_view` and `contact_message`; 2026-11-24
- **Discovered in**: PF-013
